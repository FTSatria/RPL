Kriteria ketercapaian (KKTP)

Setelah 36 JP, kamu mampu:

  1. Mendefinisikan metode pengembangan perangkat lunak (SDLC) prosedural dan berorientasi objek sesuai standar industri.
  2. Mengidentifikasi kebutuhan fungsional dan non-fungsional dari wawancara atau brief klien.
  3. Merancang Use Case Diagram dan Activity Diagram beserta skenario use case secara presisi.
  4. Merancang Class Diagram: kelas, atribut, metode, dan relasi (association, inheritance, aggregation, composition).
  5. Menerjemahkan rancangan UML ke struktur proyek di IDE dan menyusun dokumen SRS.
Pemahaman bermakna

Dalam industri, tahap perancangan dengan UML adalah fondasi. Sistem yang salah dimodelkan memicu rework kode yang mahal, arsitektur yang tidak konsisten, dan hasil akhir yang tidak sesuai kebutuhan pengguna.

M1. Metode pengembangan perangkat lunak (SDLC)

Software Development Life Cycle (SDLC) adalah tahapan kerja membangun perangkat lunak dari ide sampai dipakai dan dirawat. Tahap perancangan memakai UML berada tepat sebelum implementasi, sehingga kesalahan paham ditemukan saat murah diperbaiki.

TahapPertanyaan utamaHasil (artefak)
Analisis kebutuhanApa yang klien butuhkan?Matriks kebutuhan, SRS
DesainBagaimana sistem disusun?Use Case, Activity, Class Diagram
ImplementasiBagaimana ditulis jadi kode?Skeleton code, program
PengujianSudah sesuai kebutuhan?Hasil uji, perbaikan
PemeliharaanBagaimana tetap berjalan?Perbaikan dan pengembangan lanjutan

Prosedural vs berorientasi objek

AspekProseduralBerorientasi objek
Satuan utamaFungsi/prosedurObjek dan kelas
DataDipisah dari fungsi, mudah dipakai bersamaDibungkus bersama metode (enkapsulasi)
Penggunaan ulangMenyalin atau memanggil fungsiPewarisan dan komposisi kelas
Pemodelan umumFlowchart, DFDUML
Kaitan SKKNI (KUK 1.1 & 1.2)

Pada asesmen kamu diminta mendefinisikan dan memilih metodologi pengembangan berorientasi objek yang sesuai kebutuhan proyek, lalu menjelaskan alasannya.

M2. Analisis kebutuhan: fungsional dan non-fungsional

Kebutuhan fungsional (KF) menyatakan apa yang harus dilakukan sistem. Kebutuhan non-fungsional (KNF) menyatakan mutu yang harus dipenuhi: kecepatan, keamanan, kemudahan pakai, kompatibilitas.

Teknik mengumpulkan kebutuhan: wawancara, observasi, kuesioner, dan studi dokumen. Hasilnya dituang ke matriks spesifikasi dengan ID unik agar bisa dilacak sampai ke diagram dan kode.

IDKebutuhanJenisAktor
KF-01Sistem menyediakan login untuk Petugas dan AnggotaFRPetugas, Anggota
KF-02Petugas menambah, mengubah, menghapus, dan mencari katalog bukuFRPetugas
KF-03Petugas mencatat peminjaman dan pengembalian; sistem menghitung jatuh tempo dan denda otomatisFRPetugas
KF-04Anggota mencari ketersediaan buku berdasarkan judul/kategoriFRAnggota
KF-05Petugas mencetak laporan rekapitulasi transaksi bulananFRPetugas
KNF-01Hasil pencarian katalog tampil dalam 3 detik atau kurang (contoh)NFRAnggota
Tips analis

Kebutuhan yang baik bisa diuji. “Sistem cepat” tidak bisa diuji; “pencarian tampil ≤ 3 detik” bisa. Kebutuhan di luar lingkup (misalnya notifikasi WhatsApp) tetap dicatat agar klien tahu itu tidak termasuk.

Latihan: Simulasi 1, wawancara klien.

M3. Use Case Diagram

Use Case Diagram menggambarkan siapa (aktor) dapat melakukan apa (use case) terhadap sistem. Diagram ini jembatan antara kebutuhan klien dan perancangan.

ElemenArti
ActorPihak di luar sistem yang berinteraksi (orang atau sistem lain). Digambar sebagai manusia batang.
Use caseFungsi yang memberi hasil bernilai bagi aktor. Digambar sebagai oval, diberi nama kata kerja.
System boundaryKotak batas sistem; aktor di luar, use case di dalam.
«include»Use case dasar selalu memanggil use case yang disertakan. Panah putus-putus ke use case yang disertakan.
«extend»Perilaku tambahan yang terjadi hanya jika kondisi terpenuhi. Panah putus-putus ke use case dasar.

Hitung Jatuh Tempo selalu terjadi saat peminjaman (include). Hitung Denda hanya terjadi jika buku terlambat (extend).

Narasi use case

Diagram hanya menunjukkan keberadaan fungsi. Isi langkahnya ditulis di narasi/deskripsi use case.

NamaCatat Peminjaman
AktorPetugas Perpustakaan
PrasyaratPetugas sudah login; anggota dan buku terdaftar
Alur utama1. Petugas membuka menu Peminjaman.
2. Petugas memasukkan ID anggota dan kode buku.
3. Sistem memeriksa status anggota dan stok buku.
4. Sistem menghitung tanggal jatuh tempo.
5. Sistem menyimpan transaksi dan mengurangi stok.
6. Sistem menampilkan bukti peminjaman.
Alur alternatif3a. Anggota tidak aktif atau stok kosong: sistem menampilkan pesan kesalahan, kembali ke langkah 2.
PascakondisiTransaksi tersimpan, stok buku berkurang

Latihan: Simulasi 2, Use Case Lab.

M4. Activity Diagram

Activity Diagram menggambarkan alur kerja (workflow) langkah demi langkah. Bagian swimlane membagi tanggung jawab: aktivitas di jalur Petugas dikerjakan manusia, di jalur Sistem dikerjakan aplikasi.

SimbolArti
Lingkaran penuhInitial node: awal alur
Persegi bulatAction: satu langkah aktivitas
Belah ketupatDecision: percabangan, tiap panah diberi guard seperti “Ya” atau “Tidak”
Lingkaran bertepiFinal node: akhir alur
SwimlaneJalur tanggung jawab per aktor/sistem

Contoh: alur peminjaman buku. Jika data tidak valid, alur kembali ke input.

Cek konsistensi

Setiap langkah di narasi use case harus punya padanan di activity diagram, dan sebaliknya.

Latihan: Simulasi 3, urutkan activity diagram.

M5. Class Diagram

Class Diagram menggambarkan struktur sistem: kelas, isinya, dan hubungan antar-kelas. Kotak kelas terbagi tiga: nama, atribut, metode.

VisibilitySimbolDapat diakses dari
private-Hanya dalam kelas itu sendiri
public+Semua kelas
protected#Kelas itu dan turunannya
RelasiMaknaNotasi
AssociationDua kelas saling berhubungan (“Anggota meminjam…”)Garis lurus
InheritanceKelas turunan adalah jenis dari kelas induk (“Petugas adalah Pengguna”)Panah segitiga kosong ke induk
Aggregation“Memiliki”, bagian tetap bisa ada tanpa keseluruhanBelah ketupat kosong di sisi keseluruhan
Composition“Memiliki” yang kuat, bagian tidak ada tanpa keseluruhanBelah ketupat penuh di sisi keseluruhan

Multiplicity menyatakan jumlah objek: 1 tepat satu, 0..1 nol atau satu, 0..* nol sampai banyak, 1..* satu sampai banyak.

Untuk ringkas, parameter metode di diagram hanya ditulis namanya. Di kode dan di LKPD, tulis lengkap dengan tipe data.

Cara menemukan kelas

  1. Baca dokumen kebutuhan dan tandai kata benda.
  2. Pisahkan: yang punya data sendiri dan perilaku menjadi kelas; yang menjelaskan sebuah benda (judul, tanggal, denda) menjadi atribut.
  3. Beri tipe data dan visibility; tulis metode sebagai kata kerja.
  4. Tentukan relasi dan multiplicity, lalu cocokkan dengan Use Case Diagram: setiap use case harus ditopang oleh kelas.

Latihan: Simulasi 4, Class Lab.

M6. Dari UML ke IDE dan dokumen SRS

Class Diagram diterjemahkan menjadi skeleton code: berkas kelas dengan properti dan metode kosong (stub) yang siap diisi programmer.

Di UMLDi kode (contoh Java)
Kelas BukuBerkas Buku.java berisi public class Buku
- judul: Stringprivate String judul;
+ hapus(): voidpublic void hapus() { /* TODO */ }
Inheritance Petugas → Penggunaclass Petugas extends Pengguna
Association 1 – 0..*Atribut koleksi, misalnya List<Peminjaman>

Latihan: Simulasi 4, generator skeleton code membuat kerangka dari model perpustakaan dalam Java, PHP, atau Python.

Kerangka dokumen SRS

  1. Pendahuluan: tujuan, ruang lingkup, definisi istilah.
  2. Deskripsi umum: gambaran sistem, pengguna dan aktor, batasan.
  3. Kebutuhan fungsional: daftar KF dengan ID dan prioritas.
  4. Kebutuhan non-fungsional: kinerja, keamanan, tampilan.
  5. Model sistem: Use Case (beserta narasi), Activity, Class Diagram.
  6. Lampiran: hasil wawancara, struktur proyek di IDE.

Presentasi serah terima (client handover): jelaskan ringkas apa yang diminta klien, bagaimana sistem dimodelkan, dan bagaimana rancangan itu sudah tercermin di struktur kode. Susun SRS-mu di LKPD 4.
